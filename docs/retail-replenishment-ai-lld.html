Routing to regional agents

Step Functions calls a Lambda ring router that hashes the store ID onto a ring of virtual nodes in deterministic code, so the same store always reaches the same regional agent (session affinity) and its cache stays warm. The Strands agent does not do the hashing; it only receives the routed request.

Security

Bedrock Guardrails (Azure AI Content Safety)

  • Attached to every model call: prompt-attack filter (Azure: Prompt Shields) on any free text such as associate notes, denied topics, PII filters.
  • Filters model input and output only; capacity and reserved-SKU rules stay in code and have the final say.

IAM least privilege (Entra ID managed identities + RBAC)

  • One role per tool Lambda, scoped to its own table or endpoint; tools are read-only.
  • The agent runtime role can invoke only its 4 tools, the one Bedrock model and the guardrail; it cannot call the warehouse API.
  • Only the decision service role, after approval, can write pick lists; warehouse credentials in Secrets Manager (Azure: Key Vault).

KMS encryption (Azure Key Vault keys)

  • Customer managed KMS keys for DynamoDB, S3, Kinesis, Firehose, SQS, ElastiCache, SageMaker and CloudWatch Logs.
  • TLS in transit everywhere; key use logged in CloudTrail (Azure: Monitor activity log).

Testing

1. Load testing

  • Tooling: k6 or Locust, run at scale with Distributed Load Testing on AWS (ECS Fargate workers).
  • Scheduled path: fire runs for 2,000 stores in one window, about 200 concurrent agent sessions (example target).
  • Read path: 2,000 pick-list reads per second from store devices (example target).
  • Watch Bedrock throttling, AgentCore scaling, Step Functions concurrency and Lambda limits; include a spike (all stores at pre-close) and an 8-hour soak.

2. Latency validation

  • P50, P90 and P99 per path from k6 results, CloudWatch metrics and AWS X-Ray traces.
  • Break the run down by span: routing, each Bedrock call, each tool call, guardrails, warehouse write.
  • Pass only if every path meets the table at target load; CloudWatch alarms on P99 breaches.

3. Guardrail correctness

  • Capacity: orders that land just below, at and above the shelf’s max capacity; above must block.
  • Reserved SKU: any pull of a SKU reserved for another store must block, including partial quantities.
  • Fail closed: missing, stale or timed-out capacity, stock or reservation data blocks the order.
  • Substitutes go through the same checks; a golden set of cases must never change result.

4. Failover testing

  • Make the East agent unhealthy with AWS Fault Injection Service (or fail its health check).
  • Check only East’s ranges move to the next node, and the new owner reads state from the shared DynamoDB global table.
  • Check in-flight runs are retried without duplicate pick lists (idempotency keys).
  • Measure cache warm-up time, then bring East back and verify ranges and state return.

5. Session affinity

  • Repeated runs for the same store ID always reach the same regional agent replica.
  • Across many store IDs, key share per agent is close to even.
  • After a node joins or leaves, only the expected share of stores changes agent.

6. Audit log completeness

  • Every draft (written, blocked or substituted) has exactly one DynamoDB audit record.
  • Records hold store ID, shelf, SKU, quantity, tool results, each guardrail result, outcome, agent replica, model and timestamp.
  • Reconcile: pick lists in the warehouse system equal written audit records.

7. Regression testing

  • pytest (main framework): guardrail and decision-service logic, boundary cases with parametrize.
  • Fixtures: sample SKUs, shelves with max capacity, reservations, and sales and velocity histories in conftest; a golden set of agent transcripts replayed with stubbed Bedrock responses.
  • Playwright: only for UI checks, such as the store associate’s pick-list screen and the blocked-order view.

8. CI

  • Run the suite on every change to the agent prompt, tools, decision service or guardrail code, in AWS CodePipeline with CodeBuild or GitHub Actions.
  • A failing guardrail test blocks merge and deploy; prompt changes also run an evaluation set.
  • Results go to the CI dashboard and as CloudWatch metrics, with an alarm on any guardrail failure.

9. Limits, approval and DLQs

  • Substitute loop stops at 3 attempts and escalates; no pick list written for that shelf.
  • Approval timeout escalates and publishes nothing; edited quantities re-run guardrails.
  • Tool-call and token caps stop the run; injected failures land in each DLQ and replay without duplicates.
